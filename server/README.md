# Anchor Vault Server

A lightweight, secure secret vault and anchor management server. Supports human users (LDAP or local accounts) and automated workloads (service tokens / API keys), making it suitable for Kubernetes init containers and CI/CD pipelines.

## Quick Start

### One command

```bash
cd server/
bash start.sh
```

`start.sh` does everything automatically on first run:
1. Creates a `.env` file with randomly generated `JWT_SECRET` and `VAULT_MASTER_KEY`
2. Creates the `anc` Docker network if it doesn't exist
3. Builds and starts `anc-server` + `mongodb`
4. Waits until the server is healthy

Output:
```
>> Generating secrets in .env (first run)...
   .env created.
>> Starting services...
>> Waiting for anc-server to be healthy. ok

┌─────────────────────────────────────────────┐
│  Anchor Vault Server is up                  │
│                                             │
│  API:       http://localhost:17017          │
│  Docs:      http://localhost:17017/docs     │
│  Dashboard: http://localhost:17017/dashboard│
│  Health:    http://localhost:17017/health   │
└─────────────────────────────────────────────┘
```

### Create the first admin user

On a fresh install (no users in the database), `POST /admin/users` is open without authentication. After the first user is created, admin auth is required. **Can be done in the UI**

```bash
curl -X POST http://localhost:17017/admin/users \
  -H 'Content-Type: application/json' \
  -d '{"username": "admin", "password": "changeme", "groups": ["admins"]}'
```

### Verify it works end to end

```bash
# 1. Login
TOKEN=$(curl -s -X POST http://localhost:17017/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username": "admin", "password": "changeme"}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")

# 2. Store a secret
curl -X POST http://localhost:17017/vault/myapp/db_password \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"plaintext": "supersecret", "description": "Production DB password"}'

# 3. Read it back
curl http://localhost:17017/vault/myapp/db_password \
  -H "Authorization: Bearer $TOKEN"
# → {"id": "myapp/db_password", "plaintext": "supersecret", ...}
```

### Stop the stack

```bash
docker compose down
```

## Configuration

All configuration is via environment variables, loaded from `.env` (auto-generated by `start.sh`).

The following are **required** — the server will refuse to start without them:

| Variable | Description |
|---|---|
| `MONGO_URI` | MongoDB connection string |
| `MONGO_DB` | Database name |
| `JWT_SECRET` | Random string for JWT signing (`openssl rand -base64 32`) |
| `VAULT_MASTER_KEY` | AES master key for encryption (`openssl rand -base64 32`) |

Optional variables:

| Variable | Default | Description |
|---|---|---|
| `JWT_EXPIRE_MINUTES` | `60` | JWT token lifetime in minutes |
| `LOCAL_AUTH_ENABLED` | `true` | Enable local user authentication |
| `LDAP_AUTH_ENABLED` | `false` | Enable LDAP authentication |
| `LDAP_SERVER` | — | LDAP URL, e.g. `ldap://ldap:389` |
| `LDAP_BASE_DN` | — | e.g. `dc=company,dc=local` |
| `LDAP_ADMIN_DN` | — | LDAP admin bind DN |
| `LDAP_ADMIN_PASSWORD` | — | LDAP admin password |
| `TZ` | `Europe/Madrid` | Timezone for timestamps |

### Enabling LDAP

Uncomment the LDAP block in `docker-compose.yml`:

```yaml
environment:
  - LDAP_AUTH_ENABLED=true
  - LDAP_SERVER=ldap://ldap:389
  - LDAP_BASE_DN=dc=company,dc=local
  - LDAP_ADMIN_DN=cn=admin,dc=company,dc=local
  - LDAP_ADMIN_PASSWORD=secret
```

When both local and LDAP are enabled, `POST /auth/login` tries local first, then LDAP.

## Authentication

### 1. JWT Bearer Token (for humans)

```bash
TOKEN=$(curl -s -X POST http://localhost:17017/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username": "alice", "password": "secret"}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")

curl -H "Authorization: Bearer $TOKEN" http://localhost:17017/vault
```

Login endpoints:
- `POST /auth/login` — auto-detects local vs LDAP
- `POST /auth/login/local` — force local auth
- `POST /auth/login/ldap` — force LDAP auth

### 2. Service Token / API Key (for automation)

Service tokens are prefixed with `anc_` and carry scopes. They can be sent as a `Bearer` token or via the `X-API-Key` header (better for Kubernetes — avoids the word "Bearer" in YAML).

**Available scopes:**

| Scope | Access |
|---|---|
| `vault:read` | Read any secret |
| `vault:write` | Create and update secrets |
| `anchors:read` | Read anchors |
| `anchors:write` | Create, update, delete anchors |
| `admin` | Full access (implies all scopes) |

**Create and use a service token:**

```bash
# Create (requires admin JWT)
curl -s -X POST http://localhost:17017/admin/tokens \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name": "ci-readonly", "scopes": ["vault:read"]}'
# → {"token": "anc_abc123...", "note": "Save this token — it will not be shown again."}

# Use via X-API-Key (recommended for K8s)
curl -H "X-API-Key: anc_abc123..." http://localhost:17017/vault/myapp/db_password

# Use via Bearer
curl -H "Authorization: Bearer anc_abc123..." http://localhost:17017/vault/myapp/db_password
```

**Access control for service tokens:**
- `vault:read` → can read **all** secrets (scope is the authorization)
- To restrict a token to specific secrets only, add the token name to the secret's `users` list:
  ```json
  {"users": ["ci-readonly"]}
  ```

## API Reference

### Auth

| Method | Path | Description |
|---|---|---|
| POST | `/auth/login` | Login → JWT (auto local/LDAP) |
| POST | `/auth/login/local` | Force local login → JWT |
| POST | `/auth/login/ldap` | Force LDAP login → JWT |

### Health

| Method | Path | Description |
|---|---|---|
| GET | `/health` | Liveness probe |
| GET | `/health/ready` | Readiness probe (MongoDB + config check) |

### Vault (secrets)

Secret IDs are path-like strings: `myapp/db_password`, `prod/api_key`, etc.

| Method | Path | Scope | Description |
|---|---|---|---|
| GET | `/vault` | `vault:read` | List visible secrets (`?prefix=myapp/`) |
| POST | `/vault/{path}` | `vault:write` | Create secret |
| GET | `/vault/{path}` | `vault:read` | Get secret (`?version=N` for history) |
| PUT | `/vault/{path}` | `vault:write` | Update secret (creates new version) |
| DELETE | `/vault/{path}` | `vault:write` | Delete secret |
| GET | `/vault/{path}/versions` | `vault:read` | List version history |

**Create a secret:**
```bash
curl -X POST http://localhost:17017/vault/myapp/db_password \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "plaintext": "supersecret",
    "description": "Production DB password",
    "groups": ["devops"],
    "allow_group_edit": true
  }'
```

**Get a secret:**
```bash
curl http://localhost:17017/vault/myapp/db_password \
  -H "Authorization: Bearer $TOKEN"
# {"id": "myapp/db_password", "plaintext": "supersecret", "version": 1, ...}
```

**Versioning:**
```bash
# Update (creates version 2)
curl -X PUT http://localhost:17017/vault/myapp/db_password \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"plaintext": "newsecret"}'

# Get specific version
curl "http://localhost:17017/vault/myapp/db_password?version=1" \
  -H "Authorization: Bearer $TOKEN"

# List all versions
curl http://localhost:17017/vault/myapp/db_password/versions \
  -H "Authorization: Bearer $TOKEN"
```

**Access control fields:**
```json
{
  "groups": ["devops", "sre"],   // JWT users in these groups can read/edit
  "users": ["alice", "ci-token"],// explicit allowlist (overrides groups if set)
  "allow_group_edit": true       // allow group members to update (not just creator)
}
```

**Transferring ownership:**

The creator (or an admin) can reassign ownership of a secret to another user via `PUT`. Once transferred, the new owner has full creator rights and the previous owner loses them.

```bash
curl -X PUT http://localhost:17017/vault/myapp/db_password \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"transfer_to": "bob"}'
# → {"detail": "Secret 'myapp/db_password' updated.", "version": 1}
```

The transfer is recorded in the audit log with a `transferred_to` field.

### Anchors

| Method | Path | Scope | Description |
|---|---|---|---|
| GET | `/anchors` | `anchors:read` | List anchors (`?filter=type=local`) |
| GET | `/anchors/{name}` | `anchors:read` | Get anchor |
| POST | `/anchors` | `anchors:write` | Create or upsert anchor |
| DELETE | `/anchors/{name}` | `anchors:write` | Delete anchor |

### Admin

All endpoints require membership in the `admins` group.

| Method | Path | Description |
|---|---|---|
| POST | `/admin/tokens` | Create service token |
| GET | `/admin/tokens` | List all service tokens |
| DELETE | `/admin/tokens/{id}` | Revoke service token |
| POST | `/admin/users` | Create local user |
| GET | `/admin/users` | List all local users (no password hashes) |
| DELETE | `/admin/users/{username}` | Delete a local user |

### Web UI

A browser-based UI is available at `/ui`. No build step required (Alpine.js + Tailwind via CDN).

| Route | Description | Auth |
|---|---|---|
| `GET /ui` or `GET /ui/login` | Login page | none |
| `GET /ui/secrets` | Secrets management | any logged-in user |
| `GET /ui/users` | User management | `admins` group only |

**Secrets page features:**
- List all visible secrets with owner/shared badge
- Expand a row to see metadata (description, groups, users, allow_group_edit)
- Read plaintext (403 shown inline if access denied)
- View version history
- Create, edit, and delete secrets via modals
- Transfer ownership via the edit modal

**Users page features (admin only):**
- List all users with groups and creation date
- Create user with username, password, and groups
- Delete user with confirmation

## Kubernetes Integration

### Store the token as a K8s Secret

```bash
# Create the token
TOKEN=$(curl -s -X POST http://localhost:17017/admin/tokens \
  -H "Authorization: Bearer $ADMIN_JWT" \
  -H 'Content-Type: application/json' \
  -d '{"name": "k8s-fetcher", "scopes": ["vault:read"]}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])")

kubectl create secret generic anchor-token \
  --from-literal=token="$TOKEN"
```

### Init container example

```yaml
initContainers:
  - name: fetch-secrets
    image: curlimages/curl:latest
    env:
      - name: ANC_TOKEN
        valueFrom:
          secretKeyRef:
            name: anchor-token
            key: token
      - name: VAULT_URL
        value: "https://vault.company.internal"
    command:
      - sh
      - -c
      - |
        set -e
        curl -sf \
          -H "X-API-Key: $ANC_TOKEN" \
          "$VAULT_URL/vault/myapp/db_password" \
          | python3 -c "import sys,json; print(json.load(sys.stdin)['plaintext'])" \
          > /secrets/db_password
        echo "Secrets fetched."
    volumeMounts:
      - mountPath: /secrets
        name: secrets-vol

volumes:
  - name: secrets-vol
    emptyDir:
      medium: Memory   # keep secrets in RAM only
```

### Liveness / readiness probes for the vault server itself

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 17017
  initialDelaySeconds: 10
  periodSeconds: 30

readinessProbe:
  httpGet:
    path: /health/ready
    port: 17017
  initialDelaySeconds: 5
  periodSeconds: 10
```

## Administration

### Restart without losing data

```bash
docker compose restart anc-server
```

### View logs

```bash
docker logs -f anc-server
docker logs -f mongodb
```

### Rotating the JWT secret

Rotating invalidates all existing JWTs — users need to log in again.

```bash
# Generate a new secret
NEW_SECRET=$(openssl rand -base64 32)
# Update .env and restart
sed -i "s/^JWT_SECRET=.*/JWT_SECRET=$NEW_SECRET/" .env
docker compose --env-file .env up -d anc-server
```

### Rotating the vault master key

**This requires re-encrypting all secrets first.** Do not rotate casually — changing `VAULT_MASTER_KEY` makes all existing encrypted secrets unreadable.

### Backing up

```bash
docker exec mongodb mongodump \
  --uri "mongodb://ancadmin:ancpass@localhost:27017/" \
  --db anchor \
  --out /tmp/backup

docker cp mongodb:/tmp/backup ./backup-$(date +%Y%m%d)
```

### Viewing the audit log

Every vault operation is logged to MongoDB's `log` collection:

```bash
docker exec -it mongodb mongosh anchor \
  -u ancadmin -p ancpass --authenticationDatabase admin \
  --eval 'db.log.find({resource: "secret"}).sort({timestamp: -1}).limit(20).pretty()'
```

## Privacy Model

There are two distinct access checks for secrets:

| Function | Admin override? | Used for |
|---|---|---|
| `is_visible()` | YES (`admin` scope sees all metadata) | `GET /vault` list endpoint |
| `can_read_plaintext()` | **NO** | `GET /vault/{path}` and version history |

**Admins can list secrets for management purposes, but cannot decrypt a secret unless they are the creator or explicitly listed in `users` / `groups`.**

This means a team admin can audit what secrets exist (path, owner, expiry) without being able to read the plaintext values — secrets remain private to their owners and authorized recipients.

To grant an admin account access to a specific secret's plaintext, add their username to the secret's `users` list:

```bash
curl -X PUT http://localhost:17017/vault/myapp/db_password \
  -H "Authorization: Bearer $OWNER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"users": ["admin", "alice"]}'
```

## Upgrade Notes

### From v1 (session.py / ref.py era)

The v2 server maintains backward-compatible routes for existing CLI usage:

| Old endpoint | New endpoint |
|---|---|
| `GET /ref/list` | `GET /vault` |
| `GET /ref/get/{id}` | `GET /vault/{id}` |
| `POST /ref/set` | `POST /vault/{id}` |
| `DELETE /ref/{id}` | `DELETE /vault/{id}` |
| `POST /db/upload/{filename}` | `POST /anchors` |
| `GET /db/list` | `GET /anchors` |
| `GET /db/pull/{name}` | `GET /anchors/{name}` |

**Breaking changes:**
- `JWT_SECRET` and `VAULT_MASTER_KEY` are now **required** — server will not start without them
- Secrets encrypted with the old shared key are **not compatible** with the new per-secret HKDF derivation — migrate secrets before upgrading a production instance
- Ownership transfer now uses `transfer_to` in the PUT body (previously `created_by` in `POST /ref/update`)
